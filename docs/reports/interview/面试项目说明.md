## 1. 面试时先给的结论

### 1.1 一句话版本

> 我做的是一个基于 Telegram 的长期陪伴型 AI 导师系统。它不是单轮聊天机器人，而是把短期上下文、稳定长期记忆、历史事件召回、外部知识和后台治理拆成了独立层，目标是让系统既能稳定运行，又能逐步具备跨会话记忆能力。

### 1.2 30 秒版本

> 这个项目的重点不是“接一个大模型 API”，而是把跨会话 AI 做成工程系统。  
> 我把系统拆成了 `messages`、`profiles`、`memory_events`、`knowledge`、`sync_jobs/trace/admin` 几层。  
> 当前 `v2-min` 已经能稳定跑起来，`memory_events` 的写入、hybrid retrieval、`v1-rule-based` rerank、prompt 注入、后台治理、trace 和降级路径都接上了，`recall / write / injection / utilization / replay / degradation` 第一版 eval baseline 也已经补齐。  
> 现在的重点不是重新搭架构，而是扩真实 transcript 样本、补 `live_ai` 利用质量回归，并继续优化排序和治理策略。

### 1.3 2 分钟版本

> Affirm 是一个长期陪伴型 AI 系统，不是只回答当前这一句，而是希望跨会话“知道你是谁、你在追什么、你常卡在哪里、你之前说过什么、什么时候该想起什么”。  
> 为了避免系统越来越乱，我先做边界治理：  
> `messages` 只保留原始消息和最近上下文，`profiles` 只存稳定长期记忆，`memory_events` 只存可召回历史事件，Haystack 只做外部知识。  
> 在主链路上，用户消息进来后会先生成 `trace_id`，保存 user message，然后并行加载 `profile`、最近消息、`memory_events` 召回结果和外部知识，再统一组装 prompt 生成回复。  
> 在写链路上，我没有把长期记忆更新放在主回复同步链路里，而是回复发出后异步触发 `MemoryService`，由 LLM 产出 `profile_patch + memory_event_candidates`，更新 `profiles` 并写入 `memory_events`，再通过 `sync_jobs` 做状态化。  
> 现在这套系统已经具备召回、排序、prompt 注入、治理、追踪、降级和第一版 agent eval matrix，所以它不是 toy project，而是一个可运行、可观测、可治理、可继续演进的 AI 服务系统。

## 2. 项目到底在做什么

Affirm 想解决的是：

1. 机器人要记住最近几轮对话
2. 机器人要沉淀稳定的长期记忆
3. 机器人要在合适的时候召回过去的关键经历
4. 机器人要在需要时接入外部知识，但不能把外部知识和用户记忆混在一起
5. 机器人要能被运营、开发和我自己解释清楚，出了问题能定位，记错了能治理

## 3. 当前真实状态怎么讲

### 3.1 当前已经完成的

1. `v2-min` 最小闭环已经可运行
2. Telegram 主链路、PostgreSQL、AI 回复、后台管理都能跑起来
3. `messages` 负责原始日志和最近上下文
4. `profiles` 负责稳定长期记忆
5. `MemoryService` 在回复后异步更新长期记忆
6. `memory_events` 已完成第一版效果闭环：存储、写入、hybrid retrieval、`v1-rule-based` rerank、prompt 注入、trace、治理字段和后台动作
7. Redis、embedding provider、Knowledge RAG 都有降级路径
8. 已有第一版 agent eval matrix 和自动化测试

### 3.2 当前还没有做完的

1. `replay / utilization` 已有 fixture baseline，但真实 transcript 样本规模还不够
2. `live_ai` 利用质量评估和发布门禁还没稳定接进日常回归
3. 长期记忆效果的真实线上验证还需要更多数据
4. 排序权重、compaction 和自动治理还会继续优化

## 4. 最稳妥的表述

> 我已经把“长期记忆工程闭环”和“第一版 agent eval 闭环”做出来了。  
> 结构上已经闭环，召回、排序、治理、追踪和降级第一版也都有了。  
> 现在主要是在把 baseline 扩成更真实的 transcript、`live_ai` 回归和线上验证。
