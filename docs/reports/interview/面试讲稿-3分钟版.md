# 面试讲稿（3 分钟版）

**更新日期**：2026-06-22  
**用途**：用于项目介绍、自我介绍后的项目展开、第一轮技术面试开场

## 讲稿正文

> 我这个项目叫 Affirm，是一个运行在 Telegram 上的长期陪伴型 AI 显化导师系统。  
> 它的重点不是单轮问答，而是跨会话持续理解用户，让系统知道这个用户是谁、在追什么目标、常见阻碍是什么，以及在合适的时候想起过去发生过的关键经历。
>
> 所以我做这个项目时，核心判断不是“接一个模型 API 就结束”，而是先把上下文和记忆层拆清楚。  
> 我把系统分成几层：  
> `messages` 负责原始聊天记录和最近上下文，  
> `profiles` 负责稳定长期记忆，  
> `memory_events` 负责可检索的历史事件，  
> `Haystack` 负责外部知识，  
> `sync_jobs / trace / admin` 负责治理和可观测性。
>
> 在主链路里，用户消息进来之后，会先保存原始消息，再读取 `profile memory`、召回相关 `memory_events`、拿最近消息和外部知识，然后统一组装 prompt 生成回复。  
> 在写链路里，我没有让长期记忆更新阻塞主回复，而是回复发出后异步触发 `MemoryService`，让模型产出 `profile_patch` 和 `memory_event_candidates`，再去更新长期记忆和记录状态。
>
> 这个项目我比较看重的一点，是没有把“用户记忆”和“外部知识”混成一个检索桶。  
> 因为这两类数据的语义、权限、更新频率和治理方式都不一样。  
> 这样拆开之后，我可以更清楚地做召回、排序、注入和治理，也更容易解释系统为什么会这样回答。
>
> 另外我没有只做到“能跑”，我还补了比较完整的工程闭环。  
> 比如 `memory_events` 有召回、rerank、prompt 注入、后台治理和 trace；  
> Redis 挂了会降级到内存队列；  
> embedding provider 挂了会降级到 deterministic 向量；  
> Knowledge RAG 不可用时也不会拖垮主回复。  
> 同时我还补了一版 `recall / write / injection / utilization / replay / degradation` 的 eval baseline。
>
> 最近我又把我自己的 `harness-adopter` skill 真正接进了这个仓库。  
> 它不是业务功能，而是给已有仓库增量安装 Agent Harness：保留原有 `docs/README.md` 文档路由，补任务状态机、验证门控和会话交接工件。  
> 我会主动讲这个点，因为它说明我沉淀的不只是功能代码，还包括 AI 协作和项目接手流程。
>
> 如果继续做下一版，我不会继续在这套代码上堆功能，而是会保留产品内核和数据模型，重新搭一个更干净的 v3。  
> 因为这个项目最有价值的是“长期记忆陪伴”这个产品方向，以及它已经拆出来的记忆分层和评估思路，而不是当前这套越来越重的实现本身。
