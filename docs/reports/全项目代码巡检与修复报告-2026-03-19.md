## 2. 关键发现（按严重度）

### [high] RAG 知识检索向量参数格式不一致，可能导致知识检索实际失效

- 位置：`src/models/knowledge.js`
- 问题：
  - `Knowledge.semanticSearch()` 直接把 embedding 数组作为 `$1::vector` 参数传入；
  - 与 `Message.semanticSearch()` 的 `toVectorSql()` 处理不一致；
  - embedding 不可用时未提前返回，走 SQL 异常分支。
- 风险：知识库检索链路在部分环境中会退化为空结果，形成“RAG 看似接入但命中异常低”。
- 状态：✅ 已修复（统一 `toVectorSql` + embedding 空值提前降级 + `embedding IS NOT NULL` 过滤）。

### [high] 配置管理器把 AI Key 设为硬性必填并限制 `sk-` 前缀，与运行时降级策略冲突

- 位置：`src/config/manager.js`
- 问题：
  - `ai.apiKey` 被作为启动必填项；
  - 校验规则要求 `sk-` 前缀，不兼容部分 Provider 的 Key 格式。
- 风险：即使业务层支持 AI 不可用降级，启动阶段也可能被配置校验直接阻断。
- 状态：✅ 已修复（改为告警不阻断；校验规则改为通用长度校验）。

### [medium] `Knowledge.createBatch()` 吞错但不暴露失败明细，管理后台提示可读性不足

- 位置：`src/models/knowledge.js`、`src/admin/routes/knowledge.js`
- 问题：
  - 批量导入默认仅返回成功数组，失败原因丢失；
  - 后台只能显示成功/失败数量，无法给出可操作的错误原因。
- 风险：导入失败定位成本高，容易误判“系统稳定但数据没进库”。
- 状态：✅ 已修复（新增 `detailed` 模式返回 `successCount/failureCount/failedItems`，后台显示失败原因摘要）。

### [medium] message/knowledge 更新 embedding 时参数格式不一致

- 位置：`src/models/message.js`、`src/models/knowledge.js`
- 问题：`update()` 里把 embedding 数组直接写入 `$n::vector`，未统一 `toVectorSql()`。
- 风险：内容更新触发重嵌入时，可能出现向量更新失败或静默降级。
- 状态：✅ 已修复（更新路径统一走 `toVectorSql()`）。

### [medium] 工程脚本入口断链（`tools/*.js` 缺失）

- 位置：`package.json`、`scripts/check-status.js`、`scripts/utils/*`、`tests/test-deepseek.js`、`tests/verify-embedding.js`
- 问题：多个脚本引用不存在的 `tools` 文件，历史报告中已记录但仍未落地。
- 风险：验证/诊断链路不可执行，影响发布前自检与问题排查。
- 状态：✅ 已修复（补齐 `tools/check-status.js`、`tools/test-database.js`、`tools/verify-environment.js`、`tools/test-deepseek.js`、`tools/verify-embedding.js`，并修复 wrapper 调用与退出码）。

### [low] Admin 布局存在误导性入口与静态资源 404

- 位置：`src/admin/views/layout.ejs`
- 问题：
  - 布局包含未实现路由 `/admin/logout`、`/admin/settings`；
  - 页面引用 `/static/js/app.js` 但文件缺失。
- 风险：用户误操作进入 404，后台体验不一致。
- 状态：✅ 已修复（移除误导入口并补齐 `src/admin/static/js/app.js`）。

### [low] 部分测试/工具脚本引用路径错误

- 位置：`tests/test-vector-format.js`、`tests/validate-vector-fix.js`
- 问题：从 `tests/` 目录使用了 `./src/...` 相对路径，实际应为 `../src/...`。
- 风险：脚本运行即失败，影响本地排障。
- 状态：✅ 已修复。

## 7. 关于 `baseline-browser-mapping` 依赖问题

- 在本次环境中，`npm test` 可完整通过，未复现 `baseline-browser-mapping` 缺失问题。
- 结论：当前仓库依赖定义未出现必然断链，更可能是本地 `node_modules`/锁文件缓存状态问题。
- 建议排查顺序：
  1. 删除 `node_modules` 与 `package-lock.json` 后重新 `npm install`；
  2. 若仍报错，再执行 `npm install baseline-browser-mapping --save-dev` 验证是否为本地解析异常；
  3. 保持 Node/NPM 版本与仓库一致（Node 18+，npm 8+）。
