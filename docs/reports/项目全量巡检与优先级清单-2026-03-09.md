## 审查范围
- 代码：`src/`
- 脚本：`scripts/`、`tools/`

- 文档：`README.md`、`docs/`

## 审查方式
- 静态审查（文件结构、配置一致性、脚本可执行性、文档一致性）
- 命令验证（不修改代码）：
  - `node scripts/utils/verify-environment.js`
  - `node scripts/check-status.js`
  - `node scripts/utils/test-database.js`
  - `node tools/verify-environment.js`
  - `node tests/verify-embedding.js`
  - `npm.cmd test -- --runInBand`

## 结论摘要
当前项目主业务代码结构已成型，但“可执行运维脚本 + 文档入口 + 测试入口”存在明显断链。优先级最高的不是新功能，而是先恢复工程可用性（脚本能跑、文档可按步骤执行、测试入口可用）。

## P1（本周处理）

### 3) 配置管理器启动校验过严，可能导致服务启动即失败
- 证据：
  - `src/config/manager.js:117-121` 强制 `ai.apiKey` 必填
  - `src/config/manager.js:194` 强制 API key 必须 `startsWith('sk-')`
  - `src/config/manager.js:246` 校验失败直接 `throw`
- 影响：与 `src/config.js` 的“缺失 AI key 仅告警降级”策略冲突，特定 provider/key 格式可能直接阻断启动。
- 建议：将“启动硬失败项”与“可降级项”拆分；`ai.apiKey` 改为按 provider 规则校验。

### 4) Notion 归档时间字段疑似取错，归档展示会丢失时间
- 证据：`src/services/notion.js:288` 使用 `msg.timestamp`；消息模型常用字段为 `created_at`。
- 影响：归档页时间可能统一显示“未知时间”。
- 建议：统一消息时间字段（建议 `created_at`），并加回归测试。

### 5) 向量参数处理前后不一致，语义检索与更新逻辑存在潜在失败风险（推断）
- 证据：
  - `src/models/message.js:27-33` 在 `create` 中会 `toVectorSql(...)`
  - `src/models/message.js:217-220` 在 `update` 中直接传 `embedding` 到 `::vector`
  - `src/models/knowledge.js:27-33` 在 `create` 中会 `toVectorSql(...)`
  - `src/models/knowledge.js:166/176` 在 `semanticSearch` 中直接传 `queryEmbedding` 到 `::vector`
  - `src/models/knowledge.js:224-227` 在 `update` 中同样直接传 `embedding`
- 影响：不同路径可能出现类型转换不一致，导致检索或更新静默降级/失败。
- 建议：统一为一套 vector 入库/查询适配函数，并补充集成测试。

### 6) 测试入口存在环境耦合，当前可移植性不足
- 证据：`tests/setup.js:2` 固定读取 `/root/projects/Affirm/.env`。
- 影响：本地/CI 非该路径时测试行为不可预期。
- 建议：改为默认 `.env` 或可配置路径（如 `ENV_FILE`）。

### 7) 项目文档与实现存在错位
- 证据：`docs/project/项目概述.md:25` 写“JWT 认证”，实际是 Basic Auth（见 `src/admin/middleware/auth.js`）。
- 影响：运维与安全认知偏差。
- 建议：按代码现状修正文档，并标注“计划中能力”与“已上线能力”。
