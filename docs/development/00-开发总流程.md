## 1. 固定起手顺序

每次开始一个新任务，都按这个顺序：

1. 先跑 [01-环境启动与自检](01-环境启动与自检.md)

3. 只读对应链路文档和代码
4. 明确不要跨层写职责
5. 修改实现
6. 跑最小验证
7. 同步更新文档

### 4.2 下一阶段优先投入的方向

当前真正应该优先做的是：

1. `memory_events` 表和模型
2. 历史事件抽取
3. `memory_events` hybrid retrieval
4. Prompt 中加入“历史相关记忆片段”
5. 后台可查看和修正历史事件记忆

## 5. 当前不应优先投入的模块

下面这些不应成为主优先级：

1. 恢复旧 `messages` 语义记忆
2. 恢复旧的本地 `knowledge-vector-store`
3. 过早做复杂 rerank / 多阶段编排
4. 只优化模型提示词，却不补长期记忆检索层
5. 历史计划、旧日报、旧审计文档

## 6. 默认判断规则

### 如果任务是“机器人记不住我”

优先判断：

1. 是 `profiles` 没更新
2. 还是缺少 `memory_events` 历史召回

不要默认把问题归因到：

- Haystack
- `messages` 不够多
- 模型温度

### 如果任务是“知识回答不准”

优先判断：

1. Haystack 是否配置
2. `knowledge_chunks.metadata.rag_sync` 是否正常
3. 是否命中了 `global + user-scoped` 两类知识

### 如果任务是“回复报 AI 服务未初始化”

优先判断：

1. `.env` 是否配置了 AI provider 的 `apiKey`
2. `.env` 是否配置了对应的 `baseURL`
3. `src/config.js` 是否正确读取
4. `AIService.initialize()` 是否成功

## 7. 当前主线的完成标准

### `v2-min` 完成标准

1. Telegram 主链路能跑通
2. `messages` 写入正常
3. `profiles` 读取和更新正常
4. 回复后有 `memory_update` 类型的 `sync_jobs`
5. 后台和健康检查能看见状态

### 长期记忆效果闭环完成标准

1. `profiles` 稳定记忆可用
2. `memory_events` 能写入
3. `memory_events` 能召回
4. prompt 能注入历史事件片段
5. 能从大量历史内容里召回相关经历

## 8. 每个任务结束时至少要做的事

1. 跑对应最小验证
2. 确认没有把职责写到错误层
3. 确认没有把“目标架构”误写成“当前已实现”
4. 更新文档
5. 再准备提交
