# 07 长期记忆升级路线

**更新日期**：2026-04-16
**目标**：在保持 `v2-min` 可运行的前提下，继续把“长期记忆效果闭环”从第一版做到更稳、更可验证

## 1. 当前基线

当前仓库已经完成的能力：

1. `messages` 保存原始对话和最近上下文
2. `profiles` 保存稳定长期记忆
3. `MemoryService` 在回复后异步更新 `profiles`
4. `sync_jobs` / `trace` / Admin 提供工程治理
5. `Haystack` 可作为外部知识层接入
6. `memory_events` 表、模型和基础写入链路已落地
7. `memory_events` 已能在回复前做 hybrid retrieval，并把命中结果写入 trace metadata
8. `memory_events` 已有 `importance / recency / confidence / event_type` 的 v1 rule-based rerank
9. `memory_events` 已能注入 prompt，并参与当前轮回复生成
10. `memory_events` 已有 `status / review_status / merged_into_event_id` 治理状态与后台治理动作
11. 已有 `tools/evaluate-memory-recall.js` 与固定样本的 retrieval eval baseline
12. retrieval / rerank / prompt trace / embedding fallback / governance 已有自动化测试保护

当前缺失的关键能力：

1. 真实对话 replay eval
2. assistant 对 recalled memory 的利用质量评估
3. 更细的排序与权重优化
4. 更成熟的 compaction / 衰减 / 自动治理策略

## 2. 升级原则

推进顺序必须遵守四个原则：

1. 不破坏当前 `v2-min` 主链路可运行性
2. 不把用户记忆和 Haystack 外部知识混在一起
3. 不恢复旧 `messages` 语义记忆作为主方案
4. 先做“能跑通、能验证”的版本，再做复杂优化

## 3. Phase 0：冻结当前基线

### 目标

先确认当前 `v2-min` 是稳定的，再开始扩长期记忆。

### 要做什么

1. 确认 Telegram 主链路稳定
2. 确认 `profiles` 正常更新
3. 确认 `sync_jobs` 可见
4. 确认 Knowledge RAG 可用时接入，不可用时能降级

### 完成标准

1. 用户发消息后能收到回复
2. `messages` 有 user / assistant 日志
3. `profiles` 能看到长期记忆更新
4. `/admin/sync-jobs` 能看到 `memory_update`

## 5. Phase 2：在回复后写入历史事件

**状态**：截至 `2026-04-15` 已完成基础版；抽取质量仍需继续观察

### 目标

让每轮回复后不只更新 `profiles`，还产出 `memory_events` 候选。

### 推荐改动点

1. `src/services/memory-service.js`
2. 新增 `src/services/memory-event-service.js`
3. 新增或扩展 AI 提示，让模型同时输出：
   - `profile_patch`
   - `memory_event_candidates`

### 第一版写入原则

优先保留：

1. 明确目标变化
2. 重复阻碍模式
3. 关键突破
4. 具体承诺
5. 明确偏好信号

不要保留：

1. 一次性情绪
2. 普通寒暄
3. 外部知识内容
4. 助手脑补

### 完成标准

1. 回复后可看到 `profiles` 更新
2. 回复后可新增 `memory_events`
3. 写入失败不会阻塞主回复
4. `sync_jobs` 能记录失败和成功

当前基础版已实现：

1. `AIService` 可返回 `profile_patch + memory_event_candidates`
2. `MemoryService` 可保存 `memory_event_candidates`
3. `sync_jobs.details` 可记录 `memory_event_candidate_count` 和 `memory_event_saved_count`
4. `memory_events` 写入失败时不会中断记忆更新主流程

## 6. Phase 3：实现 `memory_events` 检索

**状态**：截至 `2026-04-15` 已完成基础版并验证

### 目标

让主链路在回复前，能够从历史事件中召回相关片段。

### 推荐新增内容

1. `src/services/memory-retrieval-service.js`
2. `src/models/memory-event.js` 检索接口
3. 必要的 embedding 生成与存储逻辑

### 第一版检索策略

推荐先做：

- `70%` 向量相似度
- `30%` 关键词权重

第一版先别加太多复杂项。
把这个版本跑通后，再考虑：

- `importance`
- `recency`
- `event_type` 权重
- rerank

### 完成标准

1. 给定用户新问题，能返回相关 `memory_events`
2. 不会召回其他用户数据
3. 没命中时返回空数组，不影响主链路

当前基础版已实现：

1. `src/services/memory-retrieval-service.js` 已提供查询 embedding + 关键词 hybrid retrieval
2. `src/models/memory-event.js` 已提供 `searchHybrid()` 与批量 `markManyRecalled()`
3. `TelegramService.loadConversationContext()` 已在回复前执行历史召回
4. assistant message metadata 已写入 `generation.recalled_memory_count` 和 `memory_refs`
5. 召回命中后会更新 `recall_count` 与 `last_recalled_at`
6. 已补 `tools/test-memory-retrieval.js` 与对应单测

本阶段验证见：

- `docs/reports/2026-04-15-memory-events-phase1-to-phase5-verification.md`

## 7. Phase 4：把历史事件注入 prompt

## 10. Phase 7：排序与权重优化

**状态**：v1 已实现并验证

### 目标

在不破坏当前主链路稳定性的前提下，让召回结果更像“应该被想起的历史”。

### 当前策略

当前实现保持“两段式”：

1. SQL 层先取 `topN` 候选，继续保留当前 `vector + keyword` hybrid retrieval
2. Node 层对 `topN` 做 rule-based rerank，再取最终 `topK`

### 当前已加入的因素

1. `importance`
2. `recency`
3. `confidence`
4. `event_type` 轻量权重
5. 基于事件内容的去重策略

### 当前完成状态

1. 排序公式已有版本号：`v1-rule-based`
2. 同一批评估样本上已可对比优化前后结果
3. 排序优化不会破坏用户隔离和空结果降级
4. assistant metadata 已能记录本轮使用的排序版本

### 这一阶段仍未覆盖的内容

1. 更多基于真实对话失败案例的权重调优
2. 更成熟的 stale-event / compaction 策略
3. 更细粒度的 ranking v2 / v3 演进计划

详细实施方案见：

- `docs/development/09-memory-events-评估排序与治理.md`

## 11. Phase 8：更成熟的记忆治理策略

**状态**：第一版已实现；自动化治理仍待继续

### 目标

把“能 CRUD”升级成“能运营、能纠偏、能压缩”的治理系统。

### 当前已落地内容

1. `status`：例如 `active / suppressed / merged / archived`
2. `review_status`：例如 `pending / verified / edited / rejected`
3. `merged_into_event_id`
4. `last_reviewed_at`
5. `metadata.governance` 操作痕迹

### 当前后台动作

1. `suppress / restore`
2. `mark verified / mark dirty`
3. `merge duplicate events`
4. 查看 source messages 与命中历史
5. 区分“逻辑下线”和“物理删除”

### 当前完成状态

1. 检索层默认不会召回 `suppressed / merged` 事件
2. 后台可以把错误记忆逻辑下线而不是直接硬删
3. 重复事件可以合并到 canonical event
4. 治理动作已留下最小审计痕迹

### 这一阶段仍未覆盖的内容

1. 自动 compaction 或自动合并
2. 更细的运营工作流和批量治理
3. 基于 recall / 质量反馈的自动衰减策略

详细实施方案见：

- `docs/development/09-memory-events-评估排序与治理.md`

## 12. 推荐实施顺序

如果只看落地优先级，建议按这个顺序做：

1. 真实 transcript replay eval
2. assistant memory utilization eval
3. ranking v2 优化
4. compaction / 自动治理

## 13. 当前不推荐的路线

这几条当前不推荐作为主线：

1. 恢复旧 `messages` 语义检索
2. 直接把用户历史塞进 Haystack
3. 一开始就做极复杂的多阶段 rerank
4. 不先做评估就盲调排序参数
5. 不做治理状态机就直接依赖物理删除

## 15. 一句话路线图

当前最稳的路线不是“让 `messages` 更像记忆”，而是：

`保留 messages 做原始日志 + 保留 profiles 做稳定记忆 + 使用 memory_events 做历史召回 + 继续补 replay eval / utilization eval + 再做 ranking v2 和自动治理`
