# 07 长期记忆升级路线

**更新日期**：2026-04-14
**目标**：在保持 `v2-min` 可运行的前提下，逐步补齐“长期记忆效果闭环”

## 1. 当前基线

当前仓库已经完成的能力：

1. `messages` 保存原始对话和最近上下文
2. `profiles` 保存稳定长期记忆
3. `MemoryService` 在回复后异步更新 `profiles`
4. `sync_jobs` / `trace` / Admin 提供工程治理
5. `Haystack` 可作为外部知识层接入

当前缺失的关键能力：

1. 独立的 `memory_events` 历史事件层
2. 从大量历史内容里召回相关经历
3. 历史事件的 hybrid retrieval
4. 历史事件进入 prompt
5. 历史记忆后台治理

## 2. 升级原则

推进顺序必须遵守四个原则：

1. 不破坏当前 `v2-min` 主链路可运行性
2. 不把用户记忆和 Haystack 外部知识混在一起
3. 不恢复旧 `messages` 语义记忆作为主方案
4. 先做“能跑通、能验证”的版本，再做复杂优化

## 3. Phase 0：冻结当前基线

### 目标

先确认当前 `v2-min` 是稳定的，再开始扩长期记忆。

### 要做什么

1. 确认 Telegram 主链路稳定
2. 确认 `profiles` 正常更新
3. 确认 `sync_jobs` 可见
4. 确认 Knowledge RAG 可用时接入，不可用时能降级

### 完成标准

1. 用户发消息后能收到回复
2. `messages` 有 user / assistant 日志
3. `profiles` 能看到长期记忆更新
4. `/admin/sync-jobs` 能看到 `memory_update`

## 4. Phase 1：新增 `memory_events` 存储层

### 目标

先把“历史事件记忆”从概念变成独立存储层。

### 推荐新增内容

1. 数据表：`memory_events`
2. 模型：`src/models/memory-event.js`
3. 迁移文件：`migrations/*memory_events*.sql`

### 第一版字段建议

- `id`
- `user_id`
- `event_type`
- `title`
- `summary`
- `detail`
- `keywords`
- `source_message_ids`
- `importance`
- `confidence`
- `happened_at`
- `last_recalled_at`
- `recall_count`
- `embedding`
- `metadata`

### 第一版不必做的事

1. 复杂冲突合并
2. 自动衰减
3. 多级摘要
4. 高级 rerank

### 完成标准

1. 可以插入一条 `memory_events`
2. 能按 `user_id` 读取
3. 有基础索引和约束

## 5. Phase 2：在回复后写入历史事件

### 目标

让每轮回复后不只更新 `profiles`，还产出 `memory_events` 候选。

### 推荐改动点

1. `src/services/memory-service.js`
2. 新增 `src/services/memory-event-service.js`
3. 新增或扩展 AI 提示，让模型同时输出：
   - `profile_patch`
   - `memory_event_candidates`

### 第一版写入原则

优先保留：

1. 明确目标变化
2. 重复阻碍模式
3. 关键突破
4. 具体承诺
5. 明确偏好信号

不要保留：

1. 一次性情绪
2. 普通寒暄
3. 外部知识内容
4. 助手脑补

### 完成标准

1. 回复后可看到 `profiles` 更新
2. 回复后可新增 `memory_events`
3. 写入失败不会阻塞主回复
4. `sync_jobs` 能记录失败和成功

## 6. Phase 3：实现 `memory_events` 检索

### 目标

让主链路在回复前，能够从历史事件中召回相关片段。

### 推荐新增内容

1. `src/services/memory-retrieval-service.js`
2. `src/models/memory-event.js` 检索接口
3. 必要的 embedding 生成与存储逻辑

### 第一版检索策略

推荐先做：

- `70%` 向量相似度
- `30%` 关键词权重

第一版先别加太多复杂项。
把这个版本跑通后，再考虑：

- `importance`
- `recency`
- `event_type` 权重
- rerank

### 完成标准

1. 给定用户新问题，能返回相关 `memory_events`
2. 不会召回其他用户数据
3. 没命中时返回空数组，不影响主链路

## 7. Phase 4：把历史事件注入 prompt

### 目标

把历史召回结果真正用于回复，而不是只存在数据库里。

### 推荐改动点

1. `src/services/telegram.js`
2. `src/services/ai.js`

### 目标顺序

`system -> profile memory -> recalled memory events -> recent messages -> knowledge -> current user message`

### 完成标准

1. prompt 中出现历史相关片段
2. 类似主题提问时，回复能引用过往相关经历
3. 外部知识仍排在用户记忆之后

## 8. Phase 5：后台治理与评估

### 目标

让长期记忆不是“只能写不能管”的黑盒。

### 推荐新增内容

1. Admin 页面查看 `memory_events`
2. 手动删除错误事件
3. 手动调整 `importance`
4. 查看某轮对话命中了哪些历史事件

### 第一版评估问题

1. 召回的是不是同一个用户
2. 召回的是不是与当前问题相关
3. 召回结果有没有明显幻觉或脏记忆
4. 召回后回复是否更像“记得这个人”

## 9. 推荐实施顺序

如果只看落地优先级，建议按这个顺序做：

1. `memory_events` 表
2. `memory_events` 写入
3. `memory_events` 检索
4. prompt 注入
5. Admin 治理
6. 评估和优化

## 10. 当前不推荐的路线

这几条当前不推荐作为主线：

1. 恢复旧 `messages` 语义检索
2. 直接把用户历史塞进 Haystack
3. 一开始就做极复杂的多阶段 rerank
4. 不做存储层就先堆 prompt 技巧

## 11. 每个阶段的最小验证

### Phase 1 验证

1. 插入一条 `memory_events`
2. 后台或脚本能读出来

### Phase 2 验证

1. 用户对话后生成 `memory_events`
2. 主回复不被阻塞

### Phase 3 验证

1. 类似主题提问时能召回相关事件
2. 不泄漏其他用户事件

### Phase 4 验证

1. 回复里能体现“记得上次说过什么”
2. 不因为记忆注入导致知识层失效

### Phase 5 验证

1. 可以人工修正错误记忆
2. 可以定位某轮回复用了哪些记忆

## 12. 一句话路线图

当前最稳的路线不是“让 `messages` 更像记忆”，而是：

`保留 messages 做原始日志 + 保留 profiles 做稳定记忆 + 新增 memory_events 做历史召回 + 保留 Haystack 做外部知识`
