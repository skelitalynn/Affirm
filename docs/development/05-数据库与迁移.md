# 05 数据库与迁移

## 1. 什么时候看这篇

当你要改这些内容时：

- 新增列
- 修改表结构
- 增加索引
- 增加唯一约束
- 调整长期记忆结构
- 调整同步任务表

## 2. 先读哪些文件

按顺序读：

1. `scripts/database/schemas/init.sql`
2. `scripts/database/migrate.js`
3. `migrations/*.sql`
4. [数据库设计](../database/数据库设计.md)

## 3. 标准流程

1. 先改 `init.sql`
2. 再新增迁移文件
3. 运行：

```bash
npm run db:migrate
```

4. 如果影响读写，再补最小验证
5. 更新对应文档

## 4. 当前最重要的表

### `profiles`

这是长期记忆主表。

当前必须保证：

- `user_id` 唯一
- `status` 有默认值 `active`
- `preferences` 是结构化 JSON

### `messages`

这是短期上下文与日志表。

当前重点关注：

- `user_id`
- `role`
- `content`
- `metadata`
- `created_at`

### `sync_jobs`

这是 v2 的治理层。

当前必须保证：

- `job_type` 非空
- `status` 有默认值
- `details` 有默认 JSON
- 按 `status`、`job_type`、`created_at` 可高效筛选

### `knowledge_chunks`

这是桥接层，不是最终检索主库。

你改它时要明确自己改的是：

- 桥接逻辑
- 后台兼容层
- 同步状态记录

而不是继续把它当最终知识引擎。

## 5. v2 新增的迁移原则

### 加唯一约束前先清理脏数据

例如 `profiles.user_id` 唯一约束，不能直接加。正确做法是：

1. 先按 `updated_at / created_at` 对重复记录排序
2. 保留最新一条
3. 删除重复记录
4. 再加唯一索引

### 给治理层字段补默认值和 NOT NULL

例如 `sync_jobs.status`、`sync_jobs.details`，应该有默认值，否则后台和健康检查会出现脏状态。

## 7. 最小验证方式

```bash
npm run db:migrate
node scripts/utils/test-database.js
```

如果改的是长期记忆结构，再验证：

- `profiles` 是否正常读写
- `profiles.preferences` 是否能保存结构化 JSON

如果改的是同步任务结构，再验证：

- Dashboard 是否能正常显示统计
- `/admin/sync-jobs` 是否能筛选和展示

## 8. 最容易出问题的改动

1. 只改迁移，不改 `init.sql`
2. 改了 `profiles` 结构，却不改 merge 逻辑
3. 给一人多 profile 留出空间
4. 把 Haystack 内部表错误地纳入应用迁移
