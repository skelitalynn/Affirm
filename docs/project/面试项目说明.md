# 面试项目说明

**更新日期**：2026-04-10  
**适用场景**：项目介绍、自我介绍中的项目经历、面试官追问、系统设计追问

## 1. 一句话介绍

Affirm 是一个运行在 Telegram 上的 AI 显化导师系统。它不是普通聊天机器人，而是一个同时具备短期上下文、长期记忆、外部知识检索和管理后台的对话系统。

## 2. 30 秒讲法

我做了一个 Telegram 上的 AI 导师系统，技术栈是 Node.js、PostgreSQL、Redis、Haystack 和 OpenAI 兼容模型。这个项目的重点不是简单接模型，而是把短期上下文、长期记忆和知识检索拆开管理，避免很多 RAG 项目里“能检索但记不住用户”“有记忆但会被历史噪声污染”的问题。

## 3. 1 分钟讲法

这个项目叫 Affirm，核心目标是做一个跨会话的对话系统。用户发消息后，系统会先读最近几轮对话作为短期上下文，再读 `profiles` 里的长期记忆，然后通过 Haystack 检索外部知识，最后统一组装 prompt 生成回复。回复完成后，系统再异步整理用户记忆并写回数据库。

我主要做的是把原来比较混乱的 RAG 和记忆设计收敛成一个可维护的闭环：`messages` 只做短期上下文，`profiles` 只做长期记忆，Haystack 只做外部知识。之后我又做了 v2 的工程化补强，把长期记忆更新抽成 `MemoryService`，把异步任务写进 `sync_jobs`，给每轮对话补了 `trace_id`，并在后台增加了同步任务管理页和系统状态面板。

## 4. 3 分钟讲法

### 业务目标

这个系统不是一次性问答，而是跨会话对话，所以必须同时解决三件事：

1. 理解当前上下文
2. 记住用户长期状态
3. 在需要时引用外部知识

### 原始问题

我接手时项目的 RAG 和记忆边界比较混乱，`messages`、`profiles`、知识库都在抢职责，结果就是：

- 历史消息很多，但不能稳定沉淀成长期记忆
- 外部知识和用户私有信息容易混在一起
- 后台虽然能存知识，但聊天侧不一定真正能用到

### 我做的 v1

我先把系统收敛成最小闭环：

- `messages`：短期上下文
- `profiles`：长期记忆
- Haystack：外部知识

然后固定 prompt 注入顺序：

`system -> profile memory -> recent messages -> knowledge -> user message`

这样至少先把功能跑通，而且每层职责清楚。

### 我做的 v2

在 v1 基础上，我又补了工程能力：

- 把长期记忆整理抽成 `MemoryService`
- 用 `sync_jobs` 跟踪 memory / knowledge 的异步任务
- 给每轮消息加 `trace_id` 和生成元数据
- 在后台补了同步任务管理页
- 在数据库层补了 `profiles.user_id` 唯一约束、`sync_jobs` 默认值和索引

所以我想表达的不是“我会写 prompt”，而是我能把一个 AI 功能做成更像正式系统的东西。

## 5. 最值得和面试官讲的难点

### 难点 1：RAG 和记忆职责混乱

很多项目会把历史消息、长期记忆、知识检索都当成 prompt 文本拼进去，短期能跑，但长期会失控。

我的处理：

- `messages` 只做短期上下文
- `profiles` 只做长期记忆
- Haystack 只做外部知识
- 固定 prompt 注入顺序

工程价值：

- 边界清晰
- 出问题容易定位
- 后续能单独演进每一层

### 难点 2：长期记忆怎么提取，才不会变成脏数据

如果把所有历史消息都当长期记忆，系统很快会被一次性情绪和短期噪声污染。

我的处理：

- 长期记忆放在 `profiles.preferences` 中，用结构化 JSON 保存
- 回复后调用 LLM 生成严格的 memory patch
- 只提取可跨会话复用的信息
- 服务端再做 merge / dedupe

工程细节：

- 主回复先完成，记忆更新后置
- 记忆更新失败不阻塞回复
- v2 中用 `MemoryService` 和 `sync_jobs` 管理这条链路

### 难点 3：知识检索外包给 Haystack 后，怎么保证迁移可控

直接把原有检索删掉切到 Haystack 风险很大。

我的处理：

- 保留 `knowledge_chunks` 作为本地桥接表
- 后台新增知识时先落本地，再同步到 Haystack
- 用 `metadata.rag_sync` 记录同步状态
- 提供 `knowledge:sync` 历史回填脚本

工程价值：

- 有迁移路径
- 有补偿机制
- 失败可排查

### 难点 4：怎么把项目从“能跑”变成“不像 toy project”

我做的不是再加一个模型能力，而是补工程层：

- `MemoryService`
- `Conversation Trace`
- `sync_jobs`
- Dashboard 和同步任务页
- 数据库约束和索引

这部分更能体现工程能力，而不是单纯 prompt 调参。

## 6. 面试官可能会问的问题

### 为什么不直接做 `messages` 向量检索当长期记忆？

因为历史消息里有大量短期噪声。长期记忆更需要精选、结构化和可维护，而不是全量召回。

### 为什么长期记忆放在 `profiles`，而不是单独一张 memory 表？

v1 先追求最小闭环，`profiles` 本身就是用户级状态载体，适合先承接长期记忆。等结构稳定、数据量更大后，再拆专门 memory 表也合理。

### 为什么把 Knowledge RAG 外包给 Haystack？

因为我想把会话和业务逻辑留在 Node 侧，把切块、检索、重排这类检索基础设施交给更合适的 RAG 框架，后续扩展成本更低。

### 已经接了 Haystack，为什么还保留 `knowledge_chunks`？

为了迁移、审计和补偿。它是桥接层，不是最终检索库。

### 长期记忆具体怎么提取？

当前做法是：回复完成后，调用 LLM 基于“最近几轮对话 + 当前已有记忆”生成严格的 memory patch，再由服务端合并进 `profiles`。

### 如果 Haystack 挂了怎么办？

主链路降级到 `profile memory + recent messages`，不会因为知识检索不可用就直接不回复。

### v2 具体做了什么？

我把长期记忆更新抽成了 `MemoryService`，把异步任务写进了 `sync_jobs`，给每轮消息补了 `trace_id` 和 generation metadata，并增加了后台同步任务页和数据库约束。

## 7. 你的项目思路可以这样说

不要一上来背技术栈，按下面顺序讲更稳：

1. 先讲问题：边界混乱，导致记忆和 RAG 都不稳定
2. 再讲原则：短期上下文、长期记忆、外部知识必须分层
3. 再讲实现：v1 先做闭环，v2 再补工程层
4. 最后讲取舍：先保证稳定和可维护，再追求更复杂的 hybrid retrieval

## 8. 不要乱说的点

如果没有真实数据，不建议硬说：

- 日活 / QPS
- 线上效果提升百分比
- 召回率提升多少
- 记忆准确率提升多少

更稳妥的说法是：

- 我重点解决的是系统结构和工程稳定性
- 结果体现在边界清晰、可降级、可追踪、可继续演进

## 9. 收尾总结

> 这个项目对我最大的锻炼，不是接了一个大模型，而是我把一个混乱的 AI 功能重构成了更像正式系统的东西。我重点解决了记忆和知识检索边界不清的问题，用 v1 先跑通闭环，再用 v2 补服务拆分、可观测性、异步任务管理和数据库治理能力。
