# 面试项目说明（增强版）

**项目**：Affirm（Telegram AI 显化导师）  
**更新日期**：2026-04-10  
**使用场景**：项目介绍、技术深挖、系统设计追问、压力面问答

## 1. 项目介绍（建议先讲这个）

Affirm 是一个跨会话 AI 对话系统，不是单轮问答机器人。  
它要同时解决四件事：短期上下文连续性、长期记忆沉淀、外部知识检索、系统可运维。

当前系统架构是分层闭环：

- `messages`：短期上下文和原始会话日志
- `profiles`：用户长期记忆（结构化 JSON）
- `knowledge_chunks + Haystack`：本地桥接层 + 外部检索引擎
- `sync_jobs`：异步任务状态记录（memory/knowledge）
- `admin`：后台管理和运维可视化

一句话价值：我把“能跑的 AI 功能”做成了“可维护、可追踪、可降级”的工程系统。

## 2. 我的项目思路（面试主线）

我按“v1 先闭环、v2 再工程化”推进，而不是一开始堆复杂能力。

### v1：先把边界收敛，保证系统跑通

- 固定职责边界：
  - `messages` 只负责短期对话
  - `profiles` 只负责长期记忆
  - Haystack 只负责外部知识
- 固定 prompt 注入顺序：
  - `system -> profile memory -> recent messages -> knowledge -> user`
- 目标：先避免职责重叠导致的不可维护问题

### v2：补工程能力，解决线上可用性问题

- `MemoryService`：把长期记忆更新从主链路抽离为异步服务
- `Conversation Trace`：每轮消息统一 `trace_id`，补 generation metadata
- `sync_jobs`：异步任务状态化（processing/completed/failed）
- 后台增强：Dashboard + `/admin/sync-jobs` 便于排障
- 健康检查增强：暴露 queue / rag / profile_memory 等状态

这套思路本质是：先建“稳定内核”，再做“智能增强”。

## 3. 我遇到的难题（可跟面试官重点聊）

这部分是最值得讲的工程实践，不是泛泛而谈。

### 难题 1：RAG 和记忆职责混乱，系统不可控

**当时问题**

- 历史消息、长期记忆、知识片段混在一起拼 prompt
- 出现问题时无法定位是检索问题、记忆问题还是生成问题

**我的做法**

- 重新定义边界：`messages` 短期、`profiles` 长期、Haystack 外部知识
- 对话入口统一加载上下文，避免“多处拼接 prompt”
- 知识检索只走 `Knowledge.semanticSearch -> ragProvider`

**工程收益**

- 故障定位从“全链路猜测”变为“分层定位”
- 模块可独立演进，改 RAG 不会牵连长期记忆模型

### 难题 2：长期记忆要可用，但不能污染、不能拖慢回复

**当时问题**

- 全量历史提取会把短期情绪噪声写进长期记忆
- 同步提取记忆会增加回复时延，影响用户体验

**我的做法**

- 记忆结构化存储在 `profiles.preferences`
- 使用 `AIService.generateMemoryPatch()` 生成严格 JSON patch
- 主回复先发送，后置调用 `MemoryService.updateLongTermMemory()`
- 异步任务写入 `sync_jobs`，失败记录 `error_message`，不阻塞主流程

**工程收益**

- 主链路可用性优先，记忆链路最终一致
- 记忆更新可追踪、可审计、可补偿

### 难题 3：接入 Haystack 后如何保证迁移安全

**当时问题**

- 如果直接切换外部检索，失败会导致知识能力“整体失效”
- 后台写入成功不代表检索侧已可用

**我的做法**

- 保留 `knowledge_chunks` 作为桥接层（而非运行时主检索库）
- 每条知识记录 `metadata.rag_sync`（pending/synced/failed）
- 批量导入走 `createBatch + syncRowsToRag`，失败项单独记录
- 提供 `knowledge:sync` 用于历史回填和补偿

**工程收益**

- 迁移有缓冲层，不是一次性“硬切”
- 写入、同步、检索三个阶段状态可见

### 难题 4：如何把 AI 项目做成可运维系统

**当时问题**

- 只有控制台日志，无法按请求链路排查
- 问题出现后很难证明在哪一层失败

**我的做法**

- 会话开始生成 `trace_id`，写入用户消息和助手消息 metadata
- 助手 metadata 记录 provider/model/knowledge refs/memory_update 策略
- `sync_jobs` 汇总异步任务状态，后台可视化展示近期任务
- `health` 暴露 `knowledge_rag`、`message_queue`、`profile_memory` 状态

**工程收益**

- 从“凭经验排障”转为“按 trace 证据排障”
- 运维与研发都能快速定位异常层

## 4. 技术链路（面试可画图讲）

### 4.1 读路径（生成回复）

1. Telegram 收到消息
2. 消息入队（BullMQ，Redis 不可用时降级内存队列）
3. 创建用户消息并写入 `trace_id`
4. 并行加载 `profile + recent messages + knowledge`
5. `AIService.prepareMessages()` 组装 prompt 并生成回复
6. 保存 assistant 消息与 generation metadata
7. 回复用户

### 4.2 写路径（长期记忆更新）

1. 回复发送成功后异步触发 `MemoryService`
2. 创建 `sync_jobs(memory_update)` 状态为 processing
3. LLM 生成 memory patch（严格 JSON）
4. `Profile.applyMemoryPatch` 合并和去重
5. 任务置 completed 或 failed

## 5. 面试官常问技术难点（含建议回答）

### Q1：为什么不把 `messages` 直接做向量记忆？

长期记忆要“可维护、可纠正、抗噪声”，不是“召回越多越好”。历史消息噪声大，直接向量化会污染长期用户画像。

### Q2：为什么长期记忆先落在 `profiles`？

v1 目标是最小闭环，`profiles` 是现成用户状态载体，改造成本低。等 schema 稳定、规模上来后再拆专门 memory 表是更稳妥路径。

### Q3：Haystack 不可用怎么办？

RAG 降级为空结果，主链路继续走 `profile memory + recent messages`，保证机器人仍能回复。可用性优先于“检索完整性”。

### Q4：如何控制异步一致性问题？

采用最终一致性：主流程先成功、异步补写、状态持久化。`sync_jobs` 让失败可见并可补偿，这比强同步导致主链路超时更符合对话场景。

### Q5：你怎么证明系统不是 toy project？

看三个维度：边界拆分（分层职责）、故障降级（不中断回复）、可观测性（trace + job 状态 + health + admin）。

### Q6：流量增长后先优化哪里？

优先主链路：队列并发治理、RAG 超时和缓存、数据库热点查询索引。记忆更新等非关键路径继续异步，避免拖慢首响应。

### Q7：为什么不用强 Agent 编排框架？

当前核心矛盾是稳定会话和工程治理，不是复杂工具链。先把主链路和观测打牢，再考虑引入更高复杂度的 Agent 能力更稳。

## 6. 你可以主动讲的工程细节（加分点）

- 队列策略：BullMQ 优先，Redis 不可用自动降级内存队列
- 失败策略：记忆更新失败不影响主回复，任务状态可回溯
- 安全策略：后台有基础认证 + CSRF + CORS 白名单
- 检索策略：知识按 global/user scope 过滤，避免权限混淆
- 追踪策略：`trace_id` 贯穿 user message -> assistant message -> memory update

## 8. 不建议夸大的口径

没有实测数据时，不要硬讲：

- DAU/QPS/时延优化百分比
- RAG 召回率、记忆准确率百分比

- 我解决的是系统边界和工程稳定性问题

## 9. 收尾总结（可直接说）

> 这个项目对我最大的锻炼，不是接入模型本身，而是把 AI 能力做成工程系统。我先通过 v1 做职责分层和功能闭环，再通过 v2 补齐异步任务管理、链路追踪、健康检查和后台可观测性，让系统在可用性、可维护性和演进性上都更像一个可上线项目。
