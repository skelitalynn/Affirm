这是当前最重要的口径。

当前已经实现的是：

> 还没有完全做到。当前已经完成稳定长期记忆和工程化闭环，下一阶段要补的是独立的历史事件记忆层和 hybrid retrieval。

## 2. 项目介绍（建议先讲这个）

Affirm 不是单轮问答机器人，而是一个长期陪伴型的显化导师系统。
它想解决五件事：

1. 短期上下文连续性
2. 稳定长期记忆沉淀
3. 大量历史经历的相关召回
4. 外部知识检索
5. 系统可运维、可追踪、可降级

当前系统分层是：

- `messages`：原始会话日志和最近上下文
- `profiles`：稳定长期记忆
- `knowledge_chunks + Haystack`：本地桥接层 + 外部知识检索引擎
- `sync_jobs`：异步任务状态记录
- `admin`：后台管理和运维可视化

下一阶段规划会新增：

- `memory_events`：可检索历史事件记忆层

一句话价值：

> 我不是只做了一个能调用模型的聊天机器人，而是把会话、长期记忆、知识检索和工程治理拆成了一个可维护的系统。

## 3. 我的项目思路（面试主线）

我按“v1 先闭环、v2 再工程化、v3 再补长期记忆效果”推进，而不是一开始堆所有复杂能力。

### v1：先把边界收敛，保证系统跑通

- `messages` 只负责短期上下文和原始日志
- `profiles` 只负责稳定长期记忆
- Haystack 只负责外部知识
- prompt 顺序先固定为：
  - `system -> profile memory -> recent messages -> knowledge -> user`

目标是：先避免职责重叠导致的不可维护问题。

### v2：补工程能力，解决线上可用性问题

- `MemoryService`：把长期记忆更新从主链路抽离为异步服务
- `Conversation Trace`：每轮消息统一 `trace_id`
- `sync_jobs`：异步任务状态化
- 后台增强：Dashboard + `/admin/sync-jobs`
- 健康检查增强：暴露 queue / rag / profile_memory 等状态

### 下一阶段：补长期记忆效果

- 新增 `memory_events`
- 对 `memory_events` 做 hybrid retrieval
- 在 prompt 中加入“历史相关记忆片段”

这套思路本质是：

- 先做“能稳定跑的系统”
- 再做“真的有长期记忆效果的产品”

## 4. 我遇到的关键难题

### 难题 1：RAG 和记忆职责混乱，系统不可控

**当时问题**

- 历史消息、长期记忆、知识片段容易被混在一起拼 prompt
- 一旦效果变差，无法定位是检索问题、记忆问题还是生成问题

**我的做法**

- 重新定义边界：`messages` 短期、`profiles` 长期、Haystack 外部知识
- 对话入口统一加载上下文，避免多处拼接 prompt
- 知识检索统一走 `Knowledge.semanticSearch -> ragProvider`

**工程收益**

- 故障定位从“全链路猜测”变成“分层定位”
- 改 RAG 时不会牵连长期记忆层

### 难题 2：长期记忆要可用，但不能污染、不能拖慢回复

**当时问题**

- 全量历史提取会把短期情绪噪声写进长期记忆
- 同步提取记忆会增加回复时延

**我的做法**

- 先把稳定记忆收敛到 `profiles.preferences`
- 使用 `AIService.generateMemoryPatch()` 生成严格 JSON patch
- 主回复先发送，后置调用 `MemoryService.updateLongTermMemory()`
- 异步任务写入 `sync_jobs`

**工程收益**

- 主链路可用性优先
- 记忆更新最终一致
- 失败可追踪、可补偿

### 难题 3：接入 Haystack 后如何保证迁移安全

**当时问题**

- 如果直接把知识检索整体切到外部侧车，失败就会导致能力整体失效
- 后台写入成功不代表检索侧可用

**我的做法**

- 保留 `knowledge_chunks` 作为桥接层
- 每条知识记录 `metadata.rag_sync`
- 批量导入走 `createBatch + syncRowsToRag`
- 保留 `knowledge:sync` 作为补偿入口

**工程收益**

- 迁移不是一次性硬切
- 写入、同步、检索三个阶段状态可见

### 难题 4：如何把 AI 项目做成可运维系统

**当时问题**

- 只有日志，没有链路级证据
- 出错后难以证明卡在哪一层

**我的做法**

- 会话开始生成 `trace_id`
- user / assistant message 统一写 metadata
- assistant metadata 记录 provider、model、knowledge refs、memory update strategy
- `sync_jobs` 汇总异步任务状态
- `health` 暴露 `knowledge_rag`、`message_queue`、`profile_memory` 状态

**工程收益**

- 从“凭经验排障”变成“按证据排障”
- 运维和研发能更快定位问题

## 5. 当前技术链路（面试可画图讲）

### 5.1 当前读路径

1. Telegram 收到消息
2. 消息入队
3. 创建用户消息并写入 `trace_id`
4. 并行加载 `profile + recent messages + knowledge`
5. `AIService.prepareMessages()` 组装 prompt
6. 生成回复
7. 保存 assistant 消息与 generation metadata
8. 回复用户

### 5.2 当前写路径

1. 回复发送成功后异步触发 `MemoryService`
2. 创建 `sync_jobs(memory_update)` 状态为 processing
3. LLM 生成 memory patch
4. `Profile.applyMemoryPatch` 合并和去重
5. 任务置 completed 或 failed

### 5.3 下一阶段目标链路

下一阶段会在当前链路上增加：

1. 历史事件抽取
2. `memory_events` 存储
3. `memory_events` hybrid retrieval
4. Prompt 中注入 `recalled memory events`

## 6. 面试官常问问题（含建议回答）

### Q1：为什么不把 `messages` 直接做向量记忆？

因为长期记忆要“可维护、可纠正、抗噪声”，不是“召回越多越好”。原始消息噪声高，直接作为主记忆库容易污染用户画像。

### Q2：为什么长期记忆先落在 `profiles`？

因为 v1 / v2-min 的目标是先把闭环跑通。`profiles` 是现成用户状态载体，改造成本低，适合先承载稳定事实。等主链路稳定后，再拆 `memory_events` 更稳。

### Q3：你是不是已经实现了真正的长期历史召回？

没有完全实现。当前已经有稳定长期记忆，但“历史事件记忆层 + hybrid retrieval”仍是下一阶段规划。这是我现在最清楚的差距。

### Q4：Haystack 不可用怎么办？

RAG 降级为空结果，主链路继续走 `profile memory + recent messages`。可用性优先于检索完整性。

### Q5：如何控制异步一致性问题？

采用最终一致性：主流程先成功、异步补写、状态持久化。`sync_jobs` 让失败可见并可补偿。

### Q6：你怎么证明系统不是 toy project？

看三个维度：

1. 边界拆分
2. 故障降级
3. 可观测性

也就是：不是只有 prompt 和模型调用，而是有服务边界、失败策略和运维接口。

### Q7：流量增长后先优化哪里？

优先主链路：

1. 队列并发治理
2. RAG 超时和缓存
3. 数据库热点查询索引
4. 非关键路径继续异步

### Q8：下一阶段最有价值的演进是什么？

不是换模型，而是补 `memory_events + hybrid retrieval`。因为当前最大差距不是回答能力，而是长期历史召回能力。

## 7. 你可以主动讲的工程细节

- 队列策略：BullMQ 优先，Redis 不可用自动降级内存队列
- 失败策略：记忆更新失败不影响主回复，任务状态可回溯
- 检索策略：知识按 `global/user scope` 过滤，避免权限混淆
- 追踪策略：`trace_id` 贯穿 user message -> assistant message -> memory update
- 配置策略：`.env -> src/config.js -> 业务模块`，避免配置散落
