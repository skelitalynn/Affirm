# 项目概述

**项目名**：Affirm  
**定位**：Telegram 上的 AI 显化导师  
**更新日期**：2026-04-10  
**当前状态**：v1 闭环已落地，v2 工程化增强已部分落地

## 1. 这个项目在做什么

Affirm 不是单轮问答机器人，而是一个跨会话对话系统。它需要同时解决四件事：

1. 记住最近几轮对话
2. 维护用户长期记忆
3. 引入外部知识
4. 让后台能看见和管理这些状态

因此它的核心不是“接一个模型”，而是把对话、记忆、知识检索拆成有边界的系统。

## 2. 当前技术栈

- 服务端：Node.js
- 数据库：PostgreSQL
- 队列：BullMQ + Redis，支持内存降级
- 外部知识检索：Haystack
- 模型接入：OpenAI 兼容 SDK
- 管理后台：Express + EJS
- 归档：Notion

## 3. 当前闭环

### v1 负责把功能跑通

| 层级 | 当前方案 | 职责 |
|------|----------|------|
| 短期上下文 | `messages` | 保存最近 N 条对话与原始日志 |
| 长期记忆 | `profiles` | 保存结构化长期记忆 |
| 外部知识 | `Haystack` | 负责知识导入、切块、检索 |
| 回答生成 | Node 主链路 | 统一拼装 prompt 并调用模型 |

注入顺序固定为：

`system -> profile memory -> recent messages -> knowledge -> user message`

### v2 负责把工程能力补齐

v2 不改变 v1 的核心边界，而是增强系统性：

- 引入 `MemoryService`，把长期记忆更新从 Telegram 主服务中抽离
- 引入 `sync_jobs`，让 memory / knowledge 的异步任务可追踪
- 给每轮对话补 `trace_id` 和生成元数据
- 在后台增加同步任务管理页，在 Dashboard 增加队列、RAG、同步任务总览
- 在数据库层补约束和索引，降低“跑得通但不稳”的风险

## 4. 当前读写链路

### 读路径

```text
Telegram message
  -> 读取 profile memory
  -> 读取 recent messages
  -> 调 Haystack 检索 knowledge
  -> 组装 prompt
  -> 生成回复
```

### 写路径

```text
user message
  -> 写入 messages
  -> 生成回复
  -> 写入 assistant message
  -> 异步触发 MemoryService
  -> 更新 profiles
  -> 写入 sync_jobs
```

## 5. 关键目录

```text
src/
├── index.js                     Telegram 主入口
├── admin/server.js              Admin 后台入口
├── services/telegram.js         对话主链路
├── services/ai.js               Prompt 组装与模型调用
├── services/memory-service.js   v2 长期记忆更新服务
├── services/conversation-trace.js  v2 对话 trace 元数据
├── services/rag/                Haystack provider / client
├── models/message.js            短期上下文与原始日志
├── models/profile.js            长期记忆载体
├── models/knowledge.js          本地桥接层 + Haystack 同步
├── models/sync-job.js           异步任务状态
└── utils/message-queue.js       队列与降级策略
```

## 6. 当前最重要的工程边界

1. 不再把 `messages` 当长期记忆库
2. 不再把 `knowledge_chunks` 当运行时主检索库
3. 长期记忆更新不阻塞主回复
4. 后台写知识时先落本地，再同步到 Haystack
5. 主链路任何一层失败都要允许降级，而不是直接把回复打挂
