# 数据库设计

> 归档说明：
> 这份文档保留的是 `2026-04-10` 时点的数据库说明，仍有结构参考价值，但不是当前文档总入口。
> 若要了解当前仓库的主入口与任务状态，优先看 [docs/README.md](../README.md) 与 [docs/PROGRESS.md](../PROGRESS.md)。

**更新日期**：2026-04-10  
**状态**：已对齐 v1 闭环与 v2 工程增强

本文档描述“本应用数据库”和“Haystack 检索索引”之间的职责边界。

## 1. 所有权边界

### 本应用直接维护的表

- `users`
- `profiles`
- `messages`
- `knowledge_chunks`
- `sync_jobs`
- `schema_migrations`

### Haystack 自己维护的索引存储

- 文档存储
- 向量索引
- 可选稀疏索引 / 重排相关存储

默认不由本应用的 `init.sql` 和 `migrations/*.sql` 直接管理。

## 2. `users`

用户主表，按 `telegram_id` 唯一识别。  
它是以下表的关联来源：

- `messages.user_id`
- `profiles.user_id`
- `knowledge_chunks.user_id`

## 3. `profiles`

`profiles` 在当前架构里不是单纯资料表，而是长期记忆层。

### 职责

- 每个用户一条长期记忆记录
- 保存 goals / status / preferences
- 承接 `MemoryService` 生成的 memory patch

### 当前字段要求

- `user_id`：唯一
- `status`：`NOT NULL`，默认 `active`
- `preferences`：`JSONB NOT NULL DEFAULT '{}'::jsonb`

### `preferences` 推荐结构

```json
{
  "memory_version": 1,
  "summary": "用户当前阶段摘要",
  "facts": ["稳定事实 1", "稳定事实 2"],
  "communication_preferences": ["偏好 1", "偏好 2"],
  "open_loops": ["待跟进 1", "待跟进 2"],
  "last_updated_at": "2026-04-10T00:00:00.000Z"
}
```

### v2 数据治理

- 迁移时先对重复 `user_id` 做去重，再加唯一索引
- 不能允许一人多 profile，否则长期记忆会失真

## 4. `messages`

`messages` 的职责很明确：

- 原始对话日志
- 最近 N 条上下文来源
- 审计与排查来源

### 当前备注

- `embedding` 字段仍保留，但不是当前主链路
- `metadata` 在 v2 中开始承载 `trace_id`、generation info、knowledge refs

## 5. `knowledge_chunks`

`knowledge_chunks` 的定位是：

- 本地桥接表
- 后台管理落库层
- Haystack 导入源
- `rag_sync` 同步状态记录层

它不再是运行时最终检索主库。

### 当前要求

- 继续保存原文、来源、用户作用域
- 继续记录 `metadata.rag_sync`
- 允许通过脚本回填到 Haystack

## 6. `sync_jobs`

`sync_jobs` 是 v2 新增的重要治理层。

### 职责

- 记录 `memory_update`
- 记录知识同步相关任务
- 提供后台列表与健康检查摘要

### 当前字段要求

- `job_type`：`NOT NULL`
- `status`：`NOT NULL DEFAULT 'pending'`
- `details`：`JSONB NOT NULL DEFAULT '{}'::jsonb`

### 当前索引

- `idx_sync_jobs_date`
- `idx_sync_jobs_status_created`
- `idx_sync_jobs_job_type_created`

这些索引直接服务于：

- Dashboard 摘要
- `/admin/sync-jobs`
- 健康检查

## 7. 当前索引重点

### 仍然关键的索引

- `idx_messages_user_created`
- `idx_sync_jobs_status_created`
- `idx_sync_jobs_job_type_created`

### 迁移期遗留索引

- `idx_messages_embedding`
- `idx_knowledge_embedding`

这些索引仍可保留，但不再代表当前主链路的核心性能点。

## 8. 修改数据库的固定规则

1. 先改 `scripts/database/schemas/init.sql`
2. 再新增 `migrations/*.sql`
3. 再更新对应文档
4. 最后补验证

## 9. 当前最常见误区

1. 继续把 `messages` 当长期记忆表
2. 继续把 `knowledge_chunks` 当最终检索主库
3. 给 `profiles` 加字段但不更新 merge 逻辑
4. 改数据库却不做去重或默认值收口
